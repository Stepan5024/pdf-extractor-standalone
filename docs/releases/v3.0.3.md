# v3.0.3: recover text without Unicode mappings

`No Unicode mapping` can indicate text loss, but PDFBox's extended glyph list
can also recover some mappings after a warning. The extractor now uses the same
extended list to distinguish these cases. It detects undecodable glyphs before
PDFBox substitutes raw character codes for simple fonts or skips composite-font
glyphs.

The old `auto` policy only used OCR when native text was shorter than 80
characters. A real PDF fixture has more than 80 readable native characters and
visible Type 3 outlines spelling `RECOVER VISIBLE TEXT 2468`, with custom glyph
names and no ToUnicode mapping. v3.0.2 loses that string while reporting success.
The baseline Unicode regression had four cases: three failed, zero errors and
zero skipped. OCR recovery, disabled OCR and unavailable OCR all exposed the defect.

## New behavior

- `auto` uses local OCR for pages containing truly undecodable glyphs, regardless
  of the amount of native text. Normal mapped pages retain native extraction.
- A page requiring Unicode recovery fails explicitly if OCR is disabled,
  unavailable, fails, or produces no text. Incomplete extraction is not reported
  as success. OCR failures retain the original cause and identify the page.
- Missing native Tesseract libraries are handled as an OCR backend failure,
  allowing the existing external Tesseract backend to run when available.
  A failed native class initialization is also handled on subsequent requests.
- A symbol resolved by PDFBox's additional glyph list remains extractable with
  OCR disabled. The `Copyright © preserved.` fixture covers this case.

## Validation and release gate

The regression checks extract and recursive combine, a long readable native
text layer with visibly undecodable glyphs, disabled/unavailable OCR, and an
additional-list mapping. The owning `adapstory-cli` implementation carries the
same change and corresponding real-PDF tests. Existing unnamed-font and JPEG2000
regressions remain in the standalone suite.

Local validation passed: 16 explicitly selected standalone cases, 10 canonical
module cases, Java and POM formatting checks. The packaged JAR under Java 17
passed both the retained font combine/split smoke and a default `eng+rus` OCR
recovery smoke (`ocrPages=1`), recovering the exact visible string. The same
smoke confirms OCR-off exits with failure and leaves no incomplete bundle.

The first Ubuntu qualification found a repeated native-load failure:
Lept4J could not load `libleptonica.so`, and the next OCR call raised
`NoClassDefFoundError` for the failed initialization. That run had 17 cases and
one error. The owning backend now treats both the initial link error and the
subsequent initialization error as backend failures, so external Tesseract
remains usable. The folder regression includes two unmapped PDFs to protect
repeated recovery. The failed run is not release-acceptance evidence.

```bash
mvn -Pfat-jar verify
bash scripts/smoke-test.sh "$PWD/target/pdf-extractor-standalone-3.0.3.jar"
```

Build with JDK 25; run with Java 17+. On Linux, local OCR requires Tesseract's
native libraries; English and Russian traineddata are bundled. Ubuntu CI installs
`tesseract-ocr` and `tesseract-ocr-rus`, reruns the suite under Java 17, and checks
both the Linux-built JAR and the exact downloadable JAR. Publish the release only
after that workflow succeeds for the release source commit.

The original user PDF is unavailable. OCR recovered the exact visible test
string; recognition accuracy on other pages depends on their visual quality.
